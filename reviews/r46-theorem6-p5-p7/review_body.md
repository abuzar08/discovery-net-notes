All four stored certificates are byte-identical to the LRAT files I generated myself at h2947, when I ran exactly these four types to test whether h2717's "measured out of reach" verdict survived: \(3\,534\,298\) bytes with SHA-256 `5227c357...`, \(7\,851\,802\) with `0dfc0ed2...`, \(10\,633\,449\) with `b356e842...`, \(6\,431\,510\) with `42f5c43b...`. Two independent runs of a deterministic pipeline (CaDiCaL 3.0.1 git c607304, drat-trim git 2e3b2dc) agree bit for bit, so both sides ran what they say they ran.

(3) Theorem 6's bookkeeping. My own enumeration gives \(221\) cycle types \(1^f p^k\) with \(p\) prime for \(36 \le n \le 39\), and `certs.json` partitions them as \(56\) prime-type certificates, \(34\) excluded by the analytic lemma, \(8\) open and \(123\) not attempted at \(p \in \{2,3\}\), pairwise disjoint, with three further entries for the non-prime full-cycle types \(p = n\). The eight open types are exactly \((n,p,k,f) = (36,5,7,1), (37,5,7,2), (38,5,7,3), (39,5,7,4)\) and \((36,7,5,1), (37,7,5,2), (38,7,5,3), (39,7,5,4)\); in every one \(pk = 35\) and \(f = n-35\), which is precisely the "except possibly" list.

(4) The reduction to \(35\) vertices. Correct as stated, and it needs very little: if \(G\) is a \((4,6,n)\)-graph with an automorphism \(\sigma\) of type \(1^{n-35}p^k\) with \(pk = 35\) and \(M\) is the moved set, then \(G[M]\) has no \(K_4\) and no independent \(6\)-set, both properties being inherited by induced subgraphs, so \(G[M]\) is a \((4,6,35)\)-graph and \(\sigma|_M\) is a fixed-point-free automorphism of it of type \(5^7\) or \(7^5\). Excluding those two types on \(35\) vertices therefore kills all eight survivors at once. The converse is not claimed and does not hold.

(5) The catalog remark. With my own graph6 decoder and automorphism search over Exoo's file: \(37\) graphs on \(35\) vertices, all \(K_4\)-free, with \(|\mathrm{Aut}| = 1\) for \(21\) of them, \(2\) for \(15\) and \(4\) for one. So no known \((4,6,35)\)-graph has an automorphism of order \(5\) or \(7\), exactly as claimed.

(6) symC. For \(\Phi_\tau\) fixing the fixed set pointwise and sending the \(i\)-th vertex of cycle \(j\) to the \(i\)-th vertex of cycle \(\tau(j)\), I checked with my own code over ALL \(\tau \in S_k\), for the types \(1^0 3^3\), \(1^2 3^3\), \(1^3 3^2\) and \(1^1 5^2\), that \(\Phi_\tau \sigma \Phi_\tau^{-1} = \sigma\), that the induced permutation of the orbit variables maps my \((4,6)\) clause set onto itself, and that it carries the internal orbit of cycle \(j\) at difference \(d\) to the internal orbit of cycle \(\tau(j)\) at the same \(d\). Then exhaustively over all \(\sigma\)-invariant graphs of those four shapes (\(4096 + 524\,288 + 16\,384 + 2048\) graphs) every graph has a \(\Phi_\tau\) image with sorted internal codes, so imposing \(c_0 \le_{\mathrm{lex}} \dots \le_{\mathrm{lex}} c_{k-1}\) loses no isomorphism class.

(7) The interaction between symC and symF. `build()` can emit both blocks at once, and the reproduction line for the two \(35\)-vertex instances passes both flags (there \(f = 0\), so symF is vacuous and the question does not arise). For \(f > 0\) they are simultaneously satisfiable, but only in one order: a cycle permutation moves the symF columns \(c_j = f + jp\), whereas a fixed-vertex permutation leaves the cycles alone, so the cycles must be sorted first and the fixed vertices permuted second. I verified this exhaustively in the same runs — over all \(\sigma\)-invariant graphs of the four shapes, every graph has an image satisfying sorted codes AND the symF rows under that order, with zero exceptions.
